# A pending audit report file is outstanding work that no installed search of what is already known reads

## Summary

The primer's knowledge table makes docs/audit-reports/ at a project's root the home of each pass of
a project audit, with the owner's ruling on each item, until the commit that carries out its last
outcome deletes the file. While it stays, it holds ruled outcomes no commit has carried out. The
installed places a session reads for what is already known name the issue and tripwire listings
only. A design could then be discussed, or a slice audited, past a ruled outcome of a pending
report. This is a prediction: no real session has shown it, and the moment is narrow, since a report
file normally leaves on the audit's own branch.

## Details

### What

Texts read, at the commit "The project audit counts convergence on old text, checks each repair
against the record, and commits each pass's report file", on which the sixth pass of the first
agentic-workflow audit ran:

- `primer@where-knowledge-goes`, the row "the evidence of one pass of a project audit, and the
  owner's ruling on each of its items": its home is one file per pass in docs/audit-reports/, as
  `skill@knowledge-architect-project-audit@record-of-an-audit` says, and it leaves when "the commit
  that carries out its last outcome, or a later commit of the same branch, deletes it".
- `primer@intent-and-claims`, its last bullet: before diagnosing, `cargo klarch issues`,
  `cargo klarch tripwires` and `cargo klarch show`.
- `skill@knowledge-architect-issue-tracking@outstanding-across-registers` and
  `skill@knowledge-architect-issue-tracking@read-before-diagnosing`: the listings.
- `agent@knowledge-architect-standing-entry-searcher@take-your-group`, the search that
  `skill@knowledge-architect-design@discussion-loop` step 1 and
  `skill@knowledge-architect-planning@working-a-slice` point 2 dispatch: it runs the two listings
  only.

A search for "audit-reports" over the installed text, `grep -rn audit-reports` over
`path@agent-skills@content/`, finds the primer's row, the audit skill's file name and the audit
workflow's preflight, and no search of what is already known. In this repository,
`instructions@verify-before-relying` lists `path@knowledge-architect@docs/audit-reports/` among the
places to look before diagnosing; an adopting project has no such line unless it writes one.

**How a pending file reaches a session other than its writer.** Every outcome of
`skill@knowledge-architect-project-audit@outcomes`, and of the agentic-workflow axis's own outcome
table, is carried out in the audit's branch; an item the owner defers, or does not rule on when
the audit stops, becomes an issue entry. So a report file is normally deleted before the audit's branch merges,
and no installed text names a route by which a pending report file reaches the main branch. The
predicted moment is therefore a session that works on the audit's branch while a report file is
pending and did not write it, or a branch that merged with a report file still present. Not
established: whether either occurs in practice.

The same mechanism, for this repository's own analyses of received retrospective files, is
`issue@agent-config@a-pending-retrospective-analysis-is-reached-by-no-standing-search`. That entry
states that the installed searches cannot name its directory, since it is this repository's own
convention. The audit report home is an installed row of the primer, so the installed text could
name it, and the fix site differs: it is the installed text, which reaches every adopting project.

Reported by the L2 and L4 lenses of the sixth pass, as a predicted gap. Not repaired by an edit,
since an instruction about how an agent behaves is added on evidence from real use, per
`design@agent-skills@additions-need-real-use`.

### Why it matters

`design@agent-skills@standing-entries-searched-before-the-work` searches every issue kind and every
tripwire before the work is designed, so that a standing entry the work bears on is ruled before
the code is written. A pending report's ruled outcome is outstanding work of the same weight that
the search does not reach. A design that duplicates or contradicts it costs the work twice.

### What would close it

A retrospective of a session, in any project that keeps a pending audit report file, that
discussed a design or audited a slice or a spec bearing on one of the file's ruled outcomes. Either
the session found the file, and the entry closes with no change; or it did not, and the installed
text names docs/audit-reports/ in one place, the listing of
`skill@knowledge-architect-issue-tracking@outstanding-across-registers`, which the primer's check
and the standing-entry search then point to, rather than in each of them. That fix makes the search
read a place its head's argument does not cover, "every issue kind and every tripwire": it is a
change of `design@agent-skills@standing-entries-searched-before-the-work`, argued under
`skill@knowledge-architect-design` before its text is written, per the backstop of
`primer@design-heads`.
